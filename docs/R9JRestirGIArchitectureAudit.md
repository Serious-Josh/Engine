# R.9J — ReSTIR GI architecture and indirect bright-pixel audit

2026-10-27. Source-grounded investigation; no implementation or runtime changes.

## 1. Executive summary

**Recommend ReSTIR GI as a gated, selectable real-time GI experiment, not as the bright-pixel correction. Implement the pixel-radiance diagnostic first.** Engine has most supporting infrastructure, and its configured RTXDI library already supplies GI reservoir/resampling code. What is missing is an Engine-specific indirect signal contract, candidate generation/reevaluation, GI bridge, resource ownership, reconnection validation and history policy. Copying the existing DI integration would not supply those pieces.

Start with primary diffuse indirect illumination, one secondary surface and conventional secondary direct-light evaluation. Initially allow reusable candidates only from diffuse secondary response; retain the complementary glossy/delta/deeper transport in the ordinary path estimator with an explicit, nonoverlapping partition. Preserve the camera reference path, primary ReSTIR DI and existing SHARC mode. Keep SHARC out of the GI prototype's candidate estimator until a common reference and reuse correctness are established.

**Bright pixels:** the newly confirmed sample-target reset result establishes that the current accumulation run retains the old distribution. It does not establish the radiance of fresh samples, whether HDR values are constant during increasing accumulation, or which term generates an outlier. Depth 2 newly evaluates secondary illumination; inverse-square point incidence, sharp secondary BRDF responses, finite throughput/PDF weights and optional SHARC suffixes remain plausible. No specific estimator defect is demonstrated. ReSTIR GI can improve sampling of valid indirect energy, but retains these radiance evaluations and can spread an erroneous or rare high-energy sample through space/time.

**RELAX contact noise:** improved indirect input could help, but the reported pre/post-RELAX difference and stable paired-visibility view do not establish an indirect-input cause. Do not change confidence strength 2. A successful GI feature and a corrected bright-pixel source require separate evidence.

Confidence ordering: high for source-verified separation of progressive and NRD histories, secondary conventional lighting and available SDK GI machinery; moderate for architectural feasibility and diffuse variance reduction; low for elimination of the reported artifacts or a shared R.9G/R.9H cause. No performance gain or artifact-removal magnitude is predicted.

### SHARC implementation and lifetime

Engine's SHARC path is a D6 moment cache, not simply an interchangeable black-box GI texture:

- `PathTraceRadianceCacheHarvest.hlsli:1–25,114–143,201–290,298–369` observes x1 and records a sampled incident suffix. Its x1 training excludes x1's own direct lighting and the immediate x1 continuation miss; later direct lighting and later misses belong to the suffix. Deferred records insert after tracing. Sparse training entry is `PathTraceRadianceCacheTrainingRayGeneration` (`PathTraceRadianceCacheTraining.hlsli:8–30`); it writes no image output.
- Render lookup/substitution is `PathTraceRadianceCacheSubstitute` (`PathTraceRadianceCacheQuery.hlsli:390–507`), called at x1 Continue (`:584–592`). Eligible material, non-delta event, query mode, accepted binding, published entry and minimum sample threshold gate it. Finite reconstructed incident radiance, normally nonnegative, is multiplied by current full/diffuse throughput and replaces a suffix. A miss term can be added separately. It is not an additive second complete GI estimator.
- `Renderer.cpp:6593–6621,6850–6879,6977–7009` orders scene epoch/generation, learning/query binding, render, optional sparse training, deferred insertion and resolve. Actual availability and library selection determine participation; the user's observations do not establish SHARC active.
- `RadianceCache/RadianceCacheD6.h:29–35,457–559` clears entry resources and writes an epoch header before access; generation state is pending until submission. `:782–812,1086–1116` orders record insertion and resolve with UAV barriers. `:285–389` retires resources/descriptors until the last-use fence completes. Query consumers read published cache history; the current frame is resolved afterward.
- `Renderer.cpp:5954–5991`, `MakeSceneLightingInputs`/`LatchSceneLighting`, removes camera, extent and sample-rate/target from world-space radiance identity. Lighting, geometry/TLAS, material, transport settings, library and cache-configuration changes remain relevant. `SceneLightingEpoch.h:5–38,100–154` documents/implements invalidation and monotonic generations. Camera movement resets progressive history without necessarily destroying the world-space cache.

### Resources, passes and scheduling

The audited path is explicitly scheduled in `Renderer::RecordPathTraceReference` and `RecordRenderFrame`, not automatically placed by a declarative render graph. No `RenderGraph` facility was found in the renderer search. Follow existing pass/resource ownership rather than proposing an assumed graph API.

`RtxdiResources.h:48–91` owns three DI arrays and an immutable neighbor table. `RtxdiResources.cpp:228–277` computes block-padded allocation and creates a structured UAV descriptor explicitly because the general Buffer views are raw. GI needs distinct layouts/descriptors/context; DI reservoirs are 24-byte records and cannot alias GI storage. Reuse immutable neighbor offsets if ownership/lifetime permits.

For new GI: G-buffer and primary DI -> candidate DXR pass -> initial/spatial/temporal reservoir passes with distinct input/output arrays -> selected-candidate visibility/resolve -> combined frame signals -> existing denoiser -> presentation. All are proposed, not existing passes. Insert UAV ordering between producer/consumer reservoir dispatches and transitions before SRV consumption. Existing split dispatch/barriers are examples (`Passes/PathTraceReferencePass.cpp:1889–1950`; `Renderer.cpp:7081–7090`). Restore Engine descriptor heaps/root bindings after NRD (`Renderer.cpp:8018–8040`). Use the current queue/submission ordering (`CommandContext.cpp:385–400`), not uncoordinated async access.

New allocations must either follow the established queue-idle resize path or fence retirement; do not free descriptors/resources referenced by in-flight work. Rotate histories only after submitted success; abandon failed recordings (`Renderer.cpp:9674–9686,11018`). Reset on extent/mode/resource generation changes and gaps. Availability failure falls back to ordinary PT and invalidates GI history. A real-time temporal GI mode must keep generating fresh candidates past the progressive target, as NRD/DLSS already do (`:6648–6656`); do not change reference-mode stopping silently.

## 3. ReSTIR GI design feasibility

### Available code and missing bridge

`CMakeLists.txt:20–38,581–585` selects/deploys the sibling `../RTXDI-Library`; this audit inspected that configured-default checkout at commit `f12037fa8e97ebc08e9e3edfd2de528ed1772a4b`. A build configured to another root must be checked separately. Local `Include/Rtxdi/GI/{Reservoir,SpatialResampling,TemporalResampling}.hlsli`, `ReSTIRGIParameters.h` and `Source/ReSTIRGI.cpp` already exist. Engine source/shader searches found no GI reservoir integration. Existing `RtxdiApplicationBridge.hlsli:1–45` and `RtxdiReuseBridge.hlsli:1–59` implement DI-domain targets/reuse, not GI callbacks.

NVIDIA's [integration guide](https://github.com/NVIDIA-RTX/RTXDI/blob/main/Doc/Integration.md) confirms GI still needs an application-provided secondary-light estimator. Treat current upstream API documentation as background; the local checkout's exact types/math govern an implementation. No dependency update is recommended for this prototype.

### Smallest mathematically defined signal

Use the first surface-to-surface diffuse-primary segment, x0 -> y=x1, and **only the diffuse component of one-secondary-vertex direct lighting** at y. Initially use static, non-transmissive diffuse-secondary materials. For eligible y, evaluate the existing diffuse BSDF lobe and direct visibility with conventional table/sun/environment sampling. Primary diffuse is Engine's energy-weighted EON lobe, not automatically Lambertian.

This restriction matters: a stored outgoing radiance value from a glossy y is view-dependent. Reconnecting y to another x0 changes y's outgoing direction. Simply reusing the old radiance produces a new bias. Engine's EON diffuse can also depend on outgoing direction. For the correctness prototype retain y's reconstructable material/hit data and the selected secondary-light sample(s), and **reevaluate y's diffuse response toward the destination receiver** for target evaluation and final shading. A deliberately Lambertian-only pilot is an alternative test domain, not a license to silently replace production EON. Admit general glossy secondary radiance only after a separately validated reevaluation/shift model. Do not claim a primary-diffuse restriction alone solves this problem.

Proposal: a dedicated primary cosine-hemisphere direction, q_omega=cos(theta0)/pi, with support wherever the primary diffuse contribution is positive; do not divide by the full-mixture PDF if sampling this dedicated strategy. Reuse existing BSDF evaluation/normal policy. The hit mapping has q_A(y)=q_omega*abs(n_y dot -omega)/distance^2. Choose either solid-angle storage plus SDK Jacobian or an explicitly area-domain reservoir derivation; do not combine both conversions twice.

For a solid-angle candidate use RGB contribution F_x=f_diff(x,omega)*cos(theta0)*L_diff,dir(y->x), with visibility handled consistently. Target p_hat_x is nonnegative luminance of that reevaluated contribution, optionally unshadowed during cheap selection with final connection visibility traced. The target must not remove support where the actual scoped integral is positive. Store unweighted radiance, original proposal density and an auditable weight convention; do not store f*cos/q and then divide by q again. Secondary sun/environment proposal/MIS factors are part of their inner direct estimator and must remain accounted once.

The complementary ordinary estimator must exclude exactly this scoped term and continue to estimate primary specular, secondary specular/multiple-scatter terms as explicitly classified, misses and deeper paths. Define the partition in code/diagnostics before reuse. An eligibility test on the sampled secondary surface must be applied identically to scoped and complementary terms. Failed/unsupported reconnection falls back to valid current candidates or the ordinary component; it must not erase transport. Initial scope can be depth 2 only until this partition is demonstrated at arbitrary depth. This is Option C below, not a claim that today's extraction already provides a standalone indirect-diffuse texture.

### Reservoir construction and reuse

For K fresh proposals, stream weights w_i=p_hat_x(y_i)/q_i, including valid zero-valued events in proposal accounting; select proportional to w_i. Initial normalized W=sum(w)/(K*p_hat_x(selected)); shade W*F_x(selected) with consistent visibility. This identity is a starting point for independent fresh candidates, not a sufficient formula for spatiotemporal reuse.

Local SDK evidence:

- `GI/Reservoir.hlsli:185–245`: single-candidate creation, combining normalized reservoirs with target × W × M, then explicit finalization. Selected target is not stored as in DI. A bare 1/M finalization omits the selected target and is wrong.
- `GI/SpatialResampling.hlsli:67–118,124–188`: primary geometry/material neighbor checks, Jacobian, destination target, second pass evaluating selected sample at contributing source surfaces and optional visibility correction.
- `GI/TemporalResampling.hlsli:137–218`: reprojection candidate, Jacobian adjustment, limited M/age, destination target and source-aware normalization.
- `Utils/Math.hlsli:153–173`: J=(cos_y,new * r_old^2)/(cos_y,old * r_new^2), the solid-angle reconnection ratio. Nonfinite J becomes zero. GI callbacks must reject degenerate geometry and unsupported connections. A finite near-singular ratio remains a risk.

Do not substitute DI's UV-domain/light-index target and normalization. A source receiver's target differs from destination BSDF/cosine/radiance. With destination-dependent secondary reevaluation, wire that reevaluation into **all** target/bias-correction queries, not just final shading. Stock GI callback signatures accept position/radiance; an Engine adapter or sidecar/reconstructable sample representation is needed to carry this information. Audit that extension against the local SDK before implementation; stock calls are not proof of correctness for a modified payload.

Final receiver-to-secondary visibility must be retraced with robust two-endpoint geometry handling. Secondary-to-light visibility is a different segment and must be reevaluated or proven unchanged. Include source-surface visibility tests required by the selected bias-correction method. Candidate creation visibility, target visibility and final visibility cannot be mixed casually; discarding selected occluded candidates or reusing stale visibility changes the estimator.

Start spatial reuse in a static scene with a separate output array, then temporal reuse. Limit neighbor count, age and represented M with a documented consistent policy; M is represented candidate mass, not a count of independent samples after correlation. Local packed M/age are 8-bit (`GI/Reservoir.hlsli:55–80`); packing saturates them. Prevent uncontrolled M growth before packing and validate normalization under limits. SDK validity only checks M!=0 (`:242–245`), so Engine must validate finite weight/radiance/PDF and denominator state as well. Do not introduce arbitrary radiance clipping; weight/Jacobian rejection policies can bias results and require explicit comparisons.

For temporal reuse, validate receiver depth/normal/material, extent/jitter conventions, previous camera and immediately preceding submitted history. Invalidate on scene/material/light/transport generation changes at first. A moving secondary object can invalidate a stored world-space sample even when its receiver is unchanged. The stock compact reservoir lacks Engine object/primitive/material identity and object-local coordinates; add sidecar identity/reevaluation or conservatively reset on geometry changes. Motion vectors alone do not solve this. No previous BVH was established in the audited GI path; using current BVH as previous geometry is defensible initially only when geometry is unchanged. Later dynamic reuse needs explicit geometry correspondence and a declared bias policy.

Algorithmic expectations are informed by [ReSTIR GI](https://research.nvidia.com/publication/2021-06_restir-gi-path-resampling-real-time-path-tracing) and [GRIS](https://research.nvidia.com/labs/rtr/publication/lin2022generalized/). The former motivates indirect-path reuse; the latter explains why correlated reuse needs stronger reasoning than independent RIS. Neither establishes that this proposed Engine estimator is unbiased or artifact-free. The [SDK GI API reference](https://github.com/NVIDIA-RTX/RTXDI/blob/main/Doc/ShaderAPI-RestirGI.md) describes normalization and optional visibility correction; local source is the implementation baseline.

## 4. Bright-pixel investigation and mechanism-by-mechanism verdict

### Updated evidence and limits

Accepted observations: no pixels at depth 1; some at depth 2; more at higher depth; present with Off/Engine and DLSS disabled; visually suppressed by RELAX; stationary until reset; sample-target change resets count/removes old pixels and new pixels appear in the new run. This last observation supplies R.9H's proposed reset evidence. It strongly supports retained sample history rather than a permanently corrupt screen location. It **does not prove constant linear HDR values while N increases**, an unchanged raw sample every frame, accumulation overflow, or a specific faulty estimator.

`PathTraceReference.hlsl:1378` seeds by pixel and accumulated sample index. `Renderer.cpp:6631–6641,8939` latches run seed and advances count after rendering. Changing target changes the accumulation key and may change run seed. Reset also changes the sampled sequence, so disappearance is not a controlled proof that the estimator was repaired. In Off, outlier E contributes E/N; after target stop it is retained indefinitely. Presentation compression can make declining HDR values appear unchanged. Effective DLSS/NRD force fresh samples; universal target-freeze claims would be incorrect.

No arbitrary radiance clamping is recommended.

### What would count as solving the issue?

Require numerical undenoised scene-linear evidence: per-sample/indirect and accumulated values at affected pixels, contribution provenance, sample count and reset/seed, plus repeated independent runs. Compare identical signal/depth/material/lighting contracts at matched cost as well as matched sample budget. Show convergence toward the ordinary high-sample reference, not just fewer white display pixels. Inspect maxima/tails, regional mean/error, spatial/temporal correlations, resets, disocclusions and dynamic response. Test without RELAX/DLSS; then measure downstream behavior separately.

If a wrong estimator term is found, demonstrate its corrected arithmetic and a focused regression. If valid variance is found, describe GI as reducing variance in its enabled component, not eliminating physically legitimate bright paths. New GI cannot fix the existing Off-mode reference unless that reference is changed, which is outside this recommendation. Keep it intact as a comparator.

## 5. RELAX contact-shadow implications

R.9G reports strength 2 improves trailing, strength 4 adds edge noise without similar responsiveness, no obvious speckles in combined pre-RELAX diffuse, visible speckles afterward, and stable stationary categorical visibility. These facts support a reconstruction/confidence/variance interaction but do not localize it to indirect samples. Visually stable compressed input can contain small stochastic variance; conversely, post-filter/history neighborhoods can produce visible noise without an upstream isolated bright pixel.

Off bright pixels live in progressive presentation. RELAX consumes per-frame combined diffuse; its input never inherits the Off accumulator (`PathTraceReference.hlsl:1455–1458`; `NrdPathTracePrepare.hlsl:437–478`). A persistent E/N speck in Off is therefore not itself the persistent texture supplied to RELAX. Its underlying sampled source might be shared, but that requires synchronized evidence.

A diffuse GI estimator could reduce indirect input variance and help contact neighborhoods if that component dominates. It would not fix primary direct visibility discontinuities, probe representation/filtering, confidence footprints, history clamping or A-trous edge behavior. Stable categorical probes only indicate no visible paired direct-visibility transitions; they do not measure indirect variance or the actual bilinear confidence consumed by RELAX. Keep strength 2 unchanged.

Reused samples are correlated. They can create stable bright patches or reservoir-age transitions, making denoisers underestimate variance or trail changes. NVIDIA's [noise/bias guide](https://github.com/NVIDIA-RTX/RTXDI/blob/main/Doc/NoiseAndBias.md) discusses stable temporal samples and clustered highlights as denoiser problems. That is a design caution, not a prediction for this scene. Judge raw scoped indirect, combined diffuse, temporal output and final RELAX output separately. Cleaner GI input is neither necessary nor sufficient proof of resolving R.9G.

## 7. Recommended architecture

Choose **C for the first experimental estimator, exposed as a selectable alternative to SHARC (A's ownership boundary)**. Do not combine with SHARC initially. The first feature is depth-2 diffuse transport with spatial reuse, then conservative temporal reuse. General glossy, delta/specular GI, arbitrary multi-bounce path reconnection and cache-radiance reuse are separate later projects.

Suggested future ownership (names are proposals): `RestirGIResources` alongside `RtxdiResources`; `RestirGICandidatePass`, `RestirGIResamplePass`, `RestirGIResolvePass` under `src/Renderer/Passes`; dedicated HLSL candidate/reuse/resolve and `RestirGIBridge.hlsli`; explicit mode/status in `RendererLightingMode.h` and `DebugUI`. Reuse `PathTraceBSDF`, `PathTraceLights`, primary-surface decoding, current/previous G-buffer and submission conventions. Do not fork BSDF math or overload DI's packed record with incompatible GI fields.

Use separate immutable inputs and writable outputs for spatial passes; maintain previous committed reservoirs and current scratch. Local packed GI record is 32 bytes (`../RTXDI-Library/Include/Rtxdi/GI/ReSTIRGIParameters.h:18–31`). Three arrays cost approximately 96 bytes per internal pixel before block padding, candidate/identity sidecars and outputs. At 1920x1080 that is about 190 MiB for reservoirs alone; this is arithmetic sizing, not a measured requirement or performance estimate. Full-precision validation payloads cost more. Decide array aliasing only after lifetimes are proven; do not begin with half-resolution/checkerboard as an additional correctness variable.

Combine the new scoped indirect with existing x0 direct diffuse and conventional complement **before** per-frame NRD preparation. Produce frame-only total/diffuse/specular and correct first-segment distances. For reused GI, distance is from the current receiver to the selected secondary point, not the source pixel's old distance; sentinel/miss/unsupported components need the existing documented treatment. RELAX raw distance and REBLUR normalized distance differ. A change to diffuse candidate strategy changes hit-distance sampling: validate it rather than copying today's “which mixture strategy was selected” sentinel logic. Never send reservoir weight, age or progressively averaged radiance as NRD radiance/confidence. Keep generated direct confidence strength 2 as-is; it does not certify indirect temporal validity.

## 9. Risks and validation requirements

- **Estimator contract:** validate measure, target support, inner direct PDFs/MIS, selected-target normalization, M limits, zero events, Jacobians and disjoint components. Source-level reuse of SDK math does not validate Engine callbacks. Do not label a realtime biased approximation unbiased because it uses ray-traced correction.
- **Dynamic state:** receiver and secondary surface are different identities. Test moving geometry/material/light changes and failed submissions. Conservative invalidation is preferable to silently stale radiance, but may erase much temporal benefit in dynamic scenes.
- **Noise versus bias:** independent-seed means and reference error expose energy shifts; pretty denoised images do not. Correlated reuse can lower apparent frame noise while preserving wrong energy or stable bright clusters. Test fresh-sample-only, initial RIS, spatial and temporal stages independently.
- **Memory/performance:** 32-byte packed reservoirs plus reevaluation metadata, bandwidth and extra connection/support rays are substantial. At one point light conventional secondary evaluation is already cheap. No evidence establishes a net speedup for the user's scene.
- **Normal/material handling:** use geometric normals for mappings/support and Engine's existing shading-normal policy for BSDFs. Reconnection near horizons and EON view dependence need explicit tests. Quantization/packing should be compared against an uncompressed diagnostic baseline before attributing artifacts to lighting.
- **NRD:** RELAX/REBLUR need noisy frame signals, proper hit distances, normal/roughness/depth and motion conventions. Reservoir history and denoiser history are separate; do not repurpose generated confidence as indirect validity. No strength/tuning changes are proposed.
- **Reference preservation:** keep current Off camera/reference path, seeds/settings and comparisons available. Experimental GI changes only its selected path. Preserve ordinary depth behavior and separate SHARC suffix approximation when matching references.

Unresolved runtime evidence: exact scene/material/light positions, active SHARC/library, actual HDR evolution during increasing N, extreme secondary sample provenance, binary/shader match and matched raw contact-edge variance. No GPU execution, captures or runtime setting changes occurred. R.9I's exact earlier specification was not supplied as a file; its name here refers to the requested pixel-radiance investigation, not a claim that an existing implementation was inspected.

## 10. Direct answers and single next step

1. **Should Engine implement ReSTIR GI?** **Yes, conditionally as a staged experimental mode.** Architectural feasibility is well supported; value must be demonstrated at matched cost. Start scoped diffuse, not general glossy/multi-bounce/cache reuse.
2. **Is it likely to improve the bright white pixels?** **It may reduce valid diffuse sampling variance in the new path, but elimination is unsupported.** Secondary incidence/BSDF defects and accumulation retention survive; reuse can spread outliers. The unchanged Off reference will still exhibit its current behavior.
3. **Could it improve RELAX contact-shadow noise?** **Plausibly, if indirect input variance is significant; confidence is low.** Existing pre/post observations do not establish that cause, and reconstruction/confidence mechanisms remain. Keep strength 2.
4. **Investigate source first or independently?** **Source diagnosis first for trustworthy estimator/quality claims; architectural planning can proceed independently.** A proven bad weight must be corrected before it becomes a reused GI candidate. Do not block planning on a complete GI prototype or call the prototype a source fix.
